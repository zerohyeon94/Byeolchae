# 06. 전사 운영 규칙

> 상태: 확정 (2026-11-09). 초안의 제안과 미결 기본값을 Zero가 그대로 확정했다. 6장의 회의 형태만 미결로 남는다
> 회사 재정의 7단계. ADR-012(15팀 41명)를 바탕으로 회사 전체에서 일이 어떻게 흐르는지 정한다. [05-운영.md](05-운영.md)는 제품 부서만 다뤘다. 05의 보고·승인 절과 다르면 이 문서를 따른다.

---

## 0. 두 가지 원칙 (2026-11-08 Zero 결정)

1. **기획은 대표가 "진행하라"고 한 뒤에 진행한다.** 무엇을, 왜, 어디까지 할지는 직원 한 명이 혼자 확정하지 않는다. 담당이 기획하고, 팀원들과 논의하고, 팀장이 확인한 뒤 기획 보고서를 대표에게 올린다. 대표가 확인하고 진행하라고 하면 그때 진행한다 (2026-11-09 Zero 결정)
   ```
   기획 → 팀원 논의 → 팀장 확인 → 기획 보고서 → [Zero 확인] → "진행" → 실행
   ```
2. **대표가 맡긴 일은 받은 사람이 끝까지 책임진다.** 팀원에게 나누거나 조사를 시켜도, 결과를 모아 대표에게 보고하는 사람은 처음 일을 받은 직원이다 (2026-11-09 Zero 확인)

나머지 규칙은 이 두 원칙을 지키면서 대표가 같은 질문을 두 번 받지 않게 하려고 둔다.

---

## 1. 결재 등급

모든 일을 대표에게 묻지는 않는다. 무엇이 "기획"인지를 이 표로 가른다.

| 등급 | 누가 정하나 | 해당하는 일 | 예 |
|------|------------|------------|----|
| A. 대표 결재 | Zero | 새로 무엇을 할지, 범위·방향, 밖으로 나가는 것, 돈, 사람, 결재받은 범위를 바꾸는 것 | 기능 기획서, 화면 디자인, 수정 방향, merge, 출시, 유튜브 영상 공개, 채용, 예산 변경 |
| B. 팀장 전결 | 담당 팀장 | 결재받은 기획 안에서 어떻게 할지 | 구현 방식, 팀원 배정, 테스트 항목, 대본의 문장 다듬기 |
| C. 기록만 | 봇 | 정해진 규칙대로 도는 일 | 정기 테스트 통과, 아침 학습, 사용량 집계 |

- B로 진행하다가 결재받은 범위를 넘어야 하면 멈추고 A로 다시 올린다. "범위를 넘는가"가 애매하면 A로 본다
- 결재 없이 A 등급 일을 진행하면 그 결과는 쓰지 않는다. 봇이 막는 것을 원칙으로 한다 (7장)

## 2. 지시와 보고의 흐름

대표가 직원에게 일을 맡길 때, 그 일이 이미 논의된 일인지 새로운 일인지에 따라 흐름이 다르다 (2026-11-09 Zero 결정).

### 2.0 이미 논의된 일: 빠른 접수

기획안이 이미 나와 대표에게 보고되었거나, 진행 방식이 확실하게 논의되어 대표가 진행하라고 한 일이다.

```
[1] 지시     Zero → 담당
[2] 빠른 접수 담당: "결재받은 ○○대로 시작한다" 한 줄
[3] 실행     담당 → 팀원에게 나눠 맡김
[4] 취합·보고 담당이 결과를 검토해 Zero에게 결과 보고
```

- 접수에서 다시 묻지 않는다. 결재받은 범위를 넘게 되면 그때 멈추고 올린다 (1장)

### 2.1 새로운 일: 접수 → 간이 틀 → 깊은 조사 → 기획 보고

대표가 처음 꺼내는 일, 아직 기획안이 없는 일이다.

```
[1] 지시     Zero → 담당 팀장
[2] 접수     팀장: "이렇게 이해했다" (목표, 모르는 것)
[3] 간이 틀  팀장이 어느 정도 틀을 잡는다 (무엇을 알아봐야 하는지, 나눌 갈래)
[4] 분배     팀장이 갈래를 팀원에게 나눠 맡긴다
[5] 수집     팀원들이 조사·작업 결과를 모아 팀장에게 올린다
[6] 분석     팀장이 결과를 확인하고 제대로 분석한다
             → 부족한 것이 있으면 [4]로 돌아가 그 부분을 더 깊게 진행한다
[7] 기획 보고 팀원 논의와 팀장 확인을 거친 기획 보고서 → Zero (3장 형식)
[8] 결정     Zero: 진행 / 수정 요청 / 반려 / 보류
             → "진행"이면 그 뒤로는 2.0의 흐름을 따른다
```

- [6]에서 [4]로 돌아가는 것은 2번까지다. 넘으면 부족한 점을 적은 채 기획 보고로 올린다 (M7)
- [7]까지 실제 만드는 일(코드, 공개 글)은 하지 않는다. 조사와 기획만 한다
- 질문이 간단하면(사실 확인, 의견 한 줄) 이 흐름을 쓰지 않고 바로 답한다. 이것이 지금의 채팅 대화다
- 팀원은 대표에게 직접 보고하지 않는다. 팀원 결과는 팀장 검토를 거친다. 대표가 팀원을 직접 부른 경우만 예외다 (2.4)
- 일을 어떻게 나누고 누가 무엇을 책임질지는 팀장이 정해서 팀원에게 준다. 위임은 팀장 → 팀원 한 단계다 (2026-11-09 Zero 결정)
- 대표가 [8]에서 수정 요청하면 [4]로 돌아간다. 같은 담당이 다시 맡는다

### 2.2 회사 전체에 내리는 지시: 비서가 배치

Zero가 담당을 정하지 않고 "회사 전체가 지금 이것을 해야 한다"고 지시하는 경우다 (2026-11-09 Zero 결정).

```
[1] 지시     Zero → 비서팀 (폴라리스, 두베)
[2] 확인     비서가 지시를 확인하고 어느 팀이 맡을 일인지 나눈다
[3] 배치     비서가 적절한 인원으로 담당자 몇 명을 뽑아 일을 맡긴다
             (팀마다 담당 한 명. 보통 팀장. 전체를 묶는 주 담당 한 명)
[4] 진행     뽑힌 담당은 2.0 또는 2.1의 흐름을 따른다
[5] 보고     주 담당이 각 담당의 보고를 모아 Zero에게 올린다
```

- 비서는 배치만 하고 일의 내용을 기획하지 않는다. 배치 결과(누가 무엇을 맡았는지)는 바로 Zero에게 알린다
- 아직 일이 배정되지 않은 팀(ADR-012의 시장·콘텐츠·재무)을 뽑아야 하면 배치 전에 Zero에게 묻는다
- 주 담당은 가장 관련 깊은 팀장이 맡는다. 비서는 배치와 진행 확인만 한다 (M8)

### 2.3 팀 사이 협조

- 팀장은 다른 팀장에게 협조를 요청할 수 있다. 다른 팀의 팀원에게 직접 일을 시키지는 않는다
- 협조 요청과 그 결과는 처음 일을 받은 담당의 보고에 함께 담긴다
- 협조 때문에 다른 팀의 결재받은 일이 늦어지면 두 팀장이 정하지 않고 Zero에게 올린다

### 2.4 대표가 팀원에게 직접 요청할 때

- Zero는 팀장을 거치지 않고 팀원에게 직접 요청할 수 있다. 팀원은 Zero에게 바로 답하고, 팀장에게는 무엇을 요청받았는지 알림이 간다 (2026-11-09 Zero 결정)
- 직접 요청이라도 A 등급 일(1장)이면 기획 보고와 Zero의 "진행"을 거친다
- **칭찬**: 아이디어, 개발, 검수 등을 특히 잘했다면 Zero가 칭찬할 수 있다. 칭찬은 기록으로 남고 팀장에게도 전해진다. 인사팀이 실적을 볼 때 함께 본다 (5장)

### 2.5 막혔을 때

| 상황 | 하는 일 |
|------|--------|
| 팀원이 막힘 | 팀장에게 바로 알린다 |
| 팀장이 혼자 풀 수 없음 | Zero에게 보고. 무엇이 막혔는지, 선택지 2개 이상, 추천 하나 |
| 환경 문제(로그인 만료, 시뮬레이터 등) | 코드로 못 고치는 일은 원인과 Zero가 할 일을 적어 바로 올린다 |
| 예산 초과 | 그 일은 멈추고 팀원 → 팀장 → 비서 순으로 요청한다 (5.1) |

막힌 일을 조용히 기다리지 않는다. 24시간 진척이 없으면 경영팀이 아침 보고에 올린다.

## 3. 보고서 형식

대표에게 올라오는 보고는 모두 같은 틀을 쓴다. 결론과 할 일을 먼저 쓴다.

| 항목 | 내용 |
|------|------|
| 결정 요청 | Zero가 정할 것 한 줄. 없으면 "보고만" |
| 결론 | 무엇을 했고 무엇을 알게 됐는지 3줄 이내 |
| 선택지와 추천 | 결정 요청이 있을 때. 선택지마다 장단점, 추천 하나와 이유 |
| 위험 | 최소 1개 (운영 규약 2.2와 같다) |
| 참여한 사람 | 누가 무엇을 했는지. 팀원·협조 팀 포함 |
| 비용 | 쓴 호출 수와 남은 예산 |
| 비서 한마디 | 4장 |
| 전문 링크 | 기획서, PR, 조사 노트 등 |

- 지금의 의견·기획 요약 JSON처럼 스키마로 검증한다. 봇은 내용을 해석하지 않고 형식만 본다
- 보고서 하나에 결정 요청은 하나만 둔다. 여러 개면 나눠 올린다

## 4. 비서의 역할

비서실장 폴라리스는 모든 일을 확인하고, 대표의 결정을 한 번 더 확인하는 참모다. 대표가 잘못된 길로 가지 않도록 마지막에 한 번 더 보는 역할이다 (2026-11-09 Zero 결정).

```
보고 → [비서 확인] → Zero 결정 → [비서 재확인] → 진행
```

- **보고 확인**: 대표에게 올라가는 보고는 모두 비서를 거친다. 보고를 다시 쓰지 않고, 대표가 놓치기 쉬운 점을 "비서 한마디"로 한두 줄 짚는다 (예: "이 기능은 가게씨 출시를 2주 늦춘다", "이번 주 세 번째 방향 변경이다")
- **결정 재확인**: Zero가 결정하면 비서가 한 번 더 본다. 문제가 없으면 조용히 넘기고, 걸리는 점이 있으면 "이 결정은 ○○와 부딪힌다, 그래도 진행할까요?"라고 한 번 묻는다. Zero가 그래도 진행한다고 하면 따른다. 같은 결정에 두 번 묻지 않는다
- 결정을 대신하거나 막지 않는다. 반대 의견도 분명히 말하되 최종 결정은 Zero가 한다
- 저녁 하루 정리에서 회사 전체를 본다: 결재 대기, 막힌 일, 대표의 결정이 늦어지는 곳
- 비서팀원 두베는 기록과 확인 대상 모으기를 돕고, 판단과 직언은 폴라리스가 한다

## 5. 경영지원 팀이 맡는 운영

ADR-012의 경영지원 묶음은 일을 만들지 않고 일이 잘 흐르게 한다.

| 팀 | 운영에서 맡는 것 |
|----|----------------|
| 경영 (레굴루스) | 진행 관리. 모든 일의 현재 단계, 막힘, 결재 대기 시간을 보고 아침·주간 보고를 만든다. 지금 봇이 DB로 만드는 보고에 팀장 해설을 붙인다 |
| 인사 (카스토르) | 직원별 실적(맡은 일, 재작업 수, 형식 오류 수, Zero의 칭찬)을 보고 채용·재배치·인격 수정을 제안한다. 제안은 A 등급 |
| 재무 (스피카) | 팀별 예산과 구독 사용량을 본다. 예산 변경 제안은 A 등급. ADR-012대로 출시 전에는 일을 맡지 않으므로 그 전에는 비서가 사용량만 보고한다 |

### 5.1 예산

- 05-운영 4장의 시작값을 팀 단위로 넓힌다. 팀장 하루 30회, 팀원 하루 15회로 시작한다 (2026-11-09 Zero 결정)
- 일이 배정되지 않은 팀(시장·콘텐츠·재무)은 예산을 쓰지 않는다
- 예산이 모자라면 아래로 올라가며 요청한다. 각 단계에서 승인하면 그 자리에서 끝나고, 넘겨야 할 때만 위로 올린다 (2026-11-09 Zero 결정)

```
팀원 → 팀장: "이 일에 ○회 더 필요하다, 이유"
팀장 → 비서: 팀장이 늘려 주기로 하면 비서에게 요청
비서 → Zero: 비서가 보고 대표의 결정이 필요하다고 판단할 때만
```

- 요청하는 동안 그 일은 멈춰 있다. 요청과 결과는 기록으로 남고 재무팀(출시 전에는 비서)이 주간 사용량과 함께 본다
- 비서는 하루 추가가 팀장 하루 예산(30회)을 넘거나 같은 일에서 두 번째 요청일 때 Zero에게 올린다 (M9)

## 7. 봇에 반영할 것

시스템을 다음처럼 바꾼다. 구현 범위와 순서는 따로 제안해 Zero 승인을 받는다.

1. **결재 기록**: 결재 요청·결정을 DB에 남긴다. 결재 번호, 등급, 담당, 상태(대기·승인·수정·반려·보류)
1-1. **Discord 결재**: 결재할 것이 생기면 Discord로 알맞게 날아오게 한다. 지금은 포럼 포스트마다 흩어진 `/approve`·`/revise`를 결재 한 건 단위로 모아, 보고 요약·비서 한마디·버튼(진행, 수정 요청, 반려, 보류)을 한 메시지로 보낸다. 어느 채널로 어떻게 보낼지는 구현 설계 때 정한다 (2026-11-09 Zero 결정: 더 구현한다)
2. **결재 전 진행 막기**: A 등급 결재가 승인되지 않은 일은 다음 단계 에이전트를 부르지 않는다. 지금 파이프라인의 gate를 결재 기록으로 일반화한다
3. **지시 명령**: 채팅에서 직원을 지정해 일을 맡기는 명령 (예: `/ask @카노푸스 경쟁 가계부 앱 조사`). 받은 직원이 접수 → 위임 → 취합 → 보고를 거친다
4. **보고서 스키마**: 3장 형식을 pydantic 스키마로
5. **위임**: 팀장이 출력 JSON에 "팀원에게 맡길 일" 목록을 내면 봇이 그 팀원을 차례로 부르고 결과를 팀장에게 돌려준다. 팀장 분석 결과에 "더 깊게 볼 것"이 있으면 같은 방식으로 한 번 더 돈다(2.1의 [6] → [4]). 봇은 목록을 옮길 뿐 판단하지 않는다
6. **전사 지시**: 비서가 출력 JSON에 배치표(팀, 담당, 맡을 일, 주 담당)를 내면 봇이 담당마다 일을 연다 (2.2)
6-1. **비서 재확인**: Zero가 결정하면 비서를 한 번 불러 재확인을 받는다. 걸리는 점이 있을 때만 Zero에게 다시 묻는다 (4장)
6-2. **칭찬과 예산 요청**: 칭찬 명령과 예산 요청 기록 (2.4, 5.1)
7. **대시보드**: 결재함(대기 중인 결재 목록)과 직원별 지금 하는 일
