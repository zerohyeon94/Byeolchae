# 03. 업무 흐름 (제품 부서)

> 상태: 확정 (2026-10-28)
> 회사 재정의 3단계. 제품 부서가 하는 일의 종류마다 흐름, 채널, 승인 지점, 맡는 팀을 정한다. 교육·비서 부서의 흐름은 제품 부서를 완성한 뒤 정한다 (2026-10-27 Zero 결정).
> 팀 이름은 헌장 3.1의 큰 틀(기획, 디자인, 개발, 검증, 테스트, 배포)을 쓴다. 팀마다 어느 에이전트를 둘지는 4단계에서 정한다.
> `[미결]`은 Zero가 아직 정하지 않은 항목이다.

---

## 1. 일의 종류

2단계의 제품 목록과 목표에서 나온 일이다.

| 종류 | 언제 생기나 | 예 | 해당 제품 |
|------|-----------|----|----------|
| 대화 | Zero가 아이디어를 꺼내거나 팀장 의견을 듣고 싶을 때 | "예산 초과 알림을 바꾸면 어떨까?" | 모두 |
| 기능 개발 | 새 기능이나 개선을 하기로 했을 때 | 위젯 추가, 화면 개편 | 모두 |
| 버그 수정 | 문제를 발견했을 때 | 크래시, 테스트 실패 | 모두. 가게씨 안정화의 중심 |
| 출시 | 첫 출시나 업데이트를 내보낼 때 | 가게씨 첫 출시, 제이데이 업데이트 | 모두 |
| 정기 테스트 | 정해진 시각마다 | 매일 밤 전체 테스트 | 모두 |
| 아이디어 관리 | 바로 하지 않을 생각을 모아 둘 때 | 오롯의 개선 아이디어 | 주로 오롯 |

## 2. 팀이 맡는 것

| 팀 | 맡는 것 | 하지 않는 것 |
|----|--------|------------|
| 기획 | 대화에서 의견, 기획서(무엇을 왜, 사용자 흐름), 문서 반영안 | 코드 변경 |
| 디자인 | 화면 디자인(화면 구성, 컴포넌트, 색·글꼴 규칙). 기획서를 받아 만든다 | 코드 변경 |
| 개발 | 대화에서 의견, 설계, 구현, 리뷰 지적 수정 | 자기 코드의 검증 |
| 검증 | 만든 것이 기획서와 맞는지, 코드가 올바른지 확인. 새 세션에서 읽기 전용 (ADR-006 검증 규칙) | 코드 수정 |
| 테스트 | 무엇을 테스트할지 정리, 테스트 실패 원인 진단, 정기 테스트 결과 보고. 테스트 명령 실행은 봇이 한다 | 코드 수정 |
| 배포 | 출시 점검 목록, 버전 번호, 릴리스 노트·스토어 설명 초안, 인증서·프로비저닝 만료 확인 | 스토어 제출 실행 (4.4) |

검증과 테스트를 이렇게 나눈다.
- **테스트**: 정해진 테스트를 실행하고(봇), 실패하면 원인을 찾는다(테스트팀). "돌아가는가"를 본다
- **검증**: 사람이 리뷰하듯 기획서와 코드를 읽고 판정한다. "맞게 만들었는가"를 본다

디자인은 처음부터 디자인팀이 맡는다 (2026-10-27 Zero 결정).

디자인 결과물은 Claude 디자인과 명세 문서를 함께 쓴다 (6장, 2026-10-28 Zero 결정).

## 3. 채널과 흐름의 관계

| 채널 | 들어오는 일 | 흐름 |
|------|-----------|------|
| `#<제품>-chat` | 대화, 아이디어 기록 | 상태 머신 없이 답만 한다 |
| `#<제품>` 포럼 | 기능 개발, 버그 수정, 출시, 정기 테스트 보고 | 포스트 하나가 흐름 하나. 단계마다 팀이 보고한다 |

채팅에서 포럼으로 넘기는 명령 (이름은 제안)

| 명령 | 하는 일 |
|------|--------|
| `/task feature <제목>` | 기능 개발 포스트를 연다. 채팅의 의견 요약을 첫머리에 옮긴다 |
| `/task bug <제목>` | 버그 수정 포스트를 연다 |
| `/release <버전>` | 출시 포스트를 연다 |
| `/idea <내용>` | 아이디어 목록에 적는다. 포스트를 열지 않는다 |

`/task`를 쓰는 것 자체가 Zero의 "하기로 한다" 결정이다. 지금의 `/decide`는 이 명령으로 대신한다.

## 4. 흐름

표기: `[Zero]`는 Zero 승인 지점, `(봇)`은 봇이 직접 하는 단계다. 괄호 안 영문은 SPEC 3.5의 단계 종류(kind)다.

### 4.1 대화

```
Zero가 #<제품>-chat에 글 → 부른 팀장이 답 → (계속 대화) → 필요하면 /task 또는 /idea
```

- `@beta`, `@alpha`처럼 부르면 그 팀장이 답한다
- 아무도 부르지 않으면 기획팀장과 개발팀장이 모두 답한다 (2026-10-27 Zero 결정). 디자인팀장 등 다른 팀장은 불렀을 때만 답한다 [제안]
- 팀장의 답은 지금의 의견 형식(입장, 결론, 근거, 위험, 제안)을 쓴다. 위험을 최소 1개 쓰는 규칙(운영 규약 2.2)도 그대로다
- 대화 기록은 Discord에만 남는다. `/task`를 할 때 봇이 요약을 포스트로 옮긴다 (운영 규약 3.1)

### 4.2 기능 개발

```
/task feature
  → 기획 (plan, 기획팀) → [Zero 기획 승인] (gate)
  → 화면 디자인 (디자인팀) → [Zero 디자인 승인] (gate)
  → 설계 (design, 개발팀) → 구현 (implement, 개발팀)
  → 테스트 (test, 봇) → 실패하면 개발팀 수정, 최대 2회
  → 검증 (review, 검증팀, 최대 3라운드) → 지적이 있으면 개발팀 수정
  → [Zero merge] (merge_gate)
  → 문서 반영 (doc_sync, 기획팀) → [Zero 문서 승인]
```

- SPEC 3.5의 `feature.yaml`에서 의견 단계(`opinions`)를 채팅으로 옮기고, 화면 디자인 단계를 더했다
- 화면 디자인은 새 단계 종류가 필요하다. SPEC 3.5의 `design`은 개발팀의 기술 설계다. 이름이 겹치므로 6단계에서 정리한다 (예: 화면 디자인 `ui_design`, 기술 설계 `tech_design`). 6단계에서 기술 설계는 기존 이름 `design`을 그대로 두고 화면 디자인만 `ui_design`으로 정했다 (SPEC 3.5, 2026-10-28)
- 화면이 바뀌지 않는 기능(데이터 처리, 성능 개선 등)은 디자인 단계를 건너뛴다. 기획 요약 JSON에 "화면 변경 있음" 표시를 두고 봇이 이 값으로 정한다 (2026-10-28 Zero 결정)
- 디자인 승인을 따로 둔다. 화면은 Zero가 직접 보고 정한다 (2026-10-28 Zero 결정)
- 헌장 3장은 새 제품의 순서를 "아이디어 → 디자인 → 기획"으로 적었다. 기능 개발은 기획서가 있어야 디자인할 수 있으므로 기획 → 디자인 순서로 둔다. 새 제품을 처음 시작하는 흐름은 제품 부서 흐름을 다 만든 뒤 따로 정한다
- 지금 구현(Phase 2 브랜치)의 설계~merge 단계를 그대로 다시 쓸 수 있다

### 4.3 버그 수정

```
/task bug
  → 진단 (diagnose, 테스트팀): 재현 방법, 원인, 수정 방향 보고
  → [Zero 수정 방향 승인] (gate)
  → 수정 (implement, 개발팀) → 테스트 (test, 봇)
  → 검증 (review, 검증팀)
  → [Zero merge] (merge_gate)
```

- 기획과 설계 단계가 없다. 진단 보고가 그 역할을 한다
- 진단 뒤 Zero 승인을 둔다 (2026-10-27 Zero 결정)
- 문서 반영은 하지 않는다. 동작이 바뀌는 수정이면 Zero가 `/task feature`로 기능 정의서를 고친다 (구현하며 `/doc` 명령은 뺐다)

### 4.4 출시

```
/release <버전>
  → 출시 점검 (test, 봇): 전체 테스트, 빌드
  → 출시 준비 (배포팀): 점검 목록, 버전 번호, 릴리스 노트·스토어 설명 초안, 인증서 만료 확인
  → [Zero 출시 승인] (gate)
  → 스토어 제출 (Zero가 직접)
```

- 릴리스 노트·스토어 설명은 외부로 나가는 글이므로 초안 → Zero 승인 규칙(헌장 4장)을 따른다
- 스토어 제출은 처음에는 Zero가 직접 한다. 봇은 준비물까지 만든다. 제출 자동화는 출시를 몇 번 해 본 뒤 정한다 (2026-10-27 Zero 결정)

### 4.5 정기 테스트

```
봇 일정 (예: 매일 03:00) → 테스트 (test, 봇)
  → 통과: 대시보드에만 기록, Discord에는 알리지 않음
  → 실패: 한 번 더 테스트 → 통과면 일시적 실패로 기록만
        → 그래도 실패 (환경 오류 포함): 진단 (diagnose, 테스트팀) → 개선 필요?
            → 필요: 포럼에 보고 포스트 (무엇이 문제인지, 무엇을 개선할지) → Zero가 /task bug 또는 환경 수정
            → 불필요: 기록만
  → 직전과 같은 실패: 진단 없이 기존 포스트에 날짜만 덧붙임
  결과는 모두 아침 보고에 한 줄로 남는다
```

- 실패해도 수정을 저절로 시작하지 않는다. 수정은 Zero가 `/task bug`로 시작한다 (사례에서 본 "자동 연쇄로 보고만 늘어나는" 실패를 피한다)
- 같은 실패가 이어지면 보고 포스트를 새로 열지 않고 기존 포스트에 덧붙인다 (2026-11-05 구현)
- 환경 문제(시뮬레이터, Xcode 등)도 원인 설명과 함께 보고한다. 코드로 고칠 수 없으니 Zero가 맥에서 직접 고친다 (2026-11-05 Zero 결정)
- 주기와 시각은 제품마다 파이프라인 YAML의 `schedule`에 적는다 (SPEC Q15)

### 4.6 아이디어 관리

```
/idea <내용> (채팅) → 아이디어 목록에 추가
아이디어 목록에서 고른 것 → 채팅에서 대화 → /task feature
```

- 아이디어 목록은 봇 DB에 두고 대시보드에서 본다 [제안]
- 볼트에 이미 `Projects/아이디어 목록.md`와 제품별 `아이디어` 폴더가 있다. 볼트에도 옮겨 적을지는 5단계(운영 방식)에서 정한다

## 6. 디자인 결과물의 형식 (질문 5)

### 6.1 Claude의 디자인 기능 (2026-10-28 조사)

- Anthropic이 2026-04에 Claude Design을 냈다. 코드베이스와 디자인 파일을 읽어 디자인 시스템(색, 글꼴, 컴포넌트, 레이아웃 규칙)을 만들고, 이후 디자인에 그 규칙을 적용한다. 완성된 디자인은 Claude Code로 넘기는 묶음(handoff)이나 HTML·PDF로 내보낸다
- 독립 사이트(claude.ai/design)는 2026-12-14에 닫히고, 같은 기능이 Claude 안의 Artifact "Design" 형식으로 옮겨졌다. Claude Code에서도 Artifact 도구로 디자인과 디자인 시스템을 만들 수 있다
- 결과물은 claude.ai의 비공개 페이지(링크)다. Zero가 Discord에서 링크를 열어 보고 승인할 수 있다
- 공개 API는 없다. 봇은 CLI(`claude -p`)를 호출하므로, 비대화형 실행에서 Artifact 도구로 디자인을 만들 수 있는지는 확인되지 않았다 [검증 필요]
- 사용량은 Claude 구독 한도에서 나간다

### 6.2 선택지

| 안 | 디자인팀이 만드는 것 | 장점 | 단점 |
|----|------------------|------|------|
| A. 명세 문서만 | 화면별 디자인 명세(md)를 앱 저장소에 커밋 | 지금 구조로 바로 됨. 검증·기록이 쉬움 | Zero가 화면을 눈으로 볼 수 없음 |
| B. Claude 디자인 + 명세 | 제품마다 디자인 시스템 1개(처음 한 번, 앱 코드에서 만듦). 기능마다 Claude 디자인(링크)과 개발팀용 명세(md) | Zero가 실제 화면을 보고 승인. 제품마다 화면 규칙이 일정함 | 비대화형 실행 가능 여부 확인이 먼저 필요. 구독 사용량 증가 |

결정: **B** (2026-10-28 Zero). 먼저 `claude -p`에서 디자인 생성이 되는지 시험하고(SPEC 검증 항목에 추가), 안 되면 A로 시작한다. 어느 쪽이든 개발팀은 앱 저장소의 명세(md)를 기준으로 구현한다. 원본은 한 곳(운영 규약 3.1)이라는 원칙에 따라 명세가 원본이고 Claude 디자인 링크는 명세에 적는다.
