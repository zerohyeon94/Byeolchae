# 2026-11-11 — Jday 정기 검증의 프로젝트 로딩 실패와 이전 보고 글 404

> 상태: 원인 확인, 빌드·테스트 표시 수정 및 로컬 빌드 복구 검증 완료. 운영 반영 전

## 증상

- 작업 #30·#32·#34는 각각 macOS 빌드를 두 번 실행했고, 여섯 번 모두 종료 코드 74로 실패했다. 테스트 수는 `null`이다. 작업 #32의 보고에서 “한 일: 없음”은 빌드 실행 기록을 빠뜨린 표현이다.
- 세 작업 모두 `prev_state=REPORTING`, `state=NEEDS_HUMAN`이다. 빌드 실행 뒤 결과를 포럼에 보고하다 `Unknown Channel` 404(10003)로 멈췄다.
- DB는 SQLite 읽기 전용 연결로 확인했고, 실행 로그는 `~/.zerosync/runs/t{30,32,34}-test-{1,2}.log`에서 확인했다.

## 원인

### Jday의 잘못된 프로젝트 그룹 소속

- 최초 조사 시 `Jday.xcodeproj/project.pbxproj`에는 `Extensions`·`Services`·`Models` 그룹이 각각 두 부모의 `children`에 들어 있었다. 실제 Xcode 오류는 `Extensions` 중복 소속을 지목한다.
- Jday의 위젯 추가 커밋 `96cc026` 직전에는 중복이 없고, 해당 커밋부터 세 그룹의 중복이 생겼다. 당시 생성기 문제인지 수동 후처리 문제인지는 이 이력만으로 확정할 수 없다.
- 현재 설치된 XcodeGen 2.46.0으로 동일한 `project.yml`을 재생성하면 세 그룹의 중복이 모두 사라진다. 현재 명세로 재생성해도 오류가 반복된다는 근거는 없다.

### 이전 정기 테스트 보고 글 재사용 실패

- 세 작업의 `diagnosis` 이벤트는 모두 `repeat_of=26`이고 같은 이전 포럼 글을 가리킨다.
- `bot/workflow/work.py`의 `_previous_report()`는 성공적으로 남은 보고 기록을 역순으로 찾는다. 후속 보고가 실패해 기록이 없으므로 계속 작업 #26의 글을 선택한다.
- `_report()`의 같은 실패 처리에서 그 글에 날짜를 덧붙이고, `bot/discord_io/client.py`의 `_webhook_for()`가 해당 스레드를 조회할 때 404가 발생했다. 이 경로는 공용 `REPORT_CHANNEL_ID`를 조회하지 않는다.
- 기존 글이 삭제됐는지, 접근 조건이 바뀌었는지는 Discord 현재 상태를 조회하지 않아 미확인이다. 로그로 확정되는 것은 당시 그 스레드를 조회할 수 없었다는 점이다.
- 같은 실패를 새 글로 복구하는 처리가 없어 매 일정마다 `NEEDS_HUMAN`이 쌓인다. `remind_waiting()`도 작업별 예외 격리가 없어 한 글의 오류가 그 회차의 나머지 재알림을 중단시킬 수 있다.

### 빌드와 테스트의 표시 혼동

- Jday 설정은 테스트 타깃이 없어 의도적으로 `xcodebuild build`를 실행한다. 생성된 타깃도 앱 두 개와 위젯 하나이며 테스트 타깃은 없다.
- 수정 전 `TestReport.passed`는 종료 코드가 정상이고 실패 수가 없으면 참이며, `render_test_report()`는 실행된 테스트가 없어도 “테스트 통과 — ?개”라고 표시했다.
- 세 담당자 보고 본문은 모두 기획팀장 수신함 DB에 저장돼 있고 `read_at`은 비어 있다. 내부 수신함 저장과 Discord 포럼 게시 성공은 별개다.

## 해결 검증

원본 Jday 저장소 대신 `/private/tmp/zerosync-jday-check-eszwutg6`에 소스와 명세를 복사한 뒤 다음을 수행했다.

1. `xcodegen generate --spec project.yml` 실행 성공.
2. 생성된 `project.pbxproj`를 `plutil`로 읽어 그룹별 부모 참조를 집계했다. 다중 부모 그룹이 하나도 없었다.
3. 아래 macOS 빌드를 실행해 종료 코드 0과 `BUILD SUCCEEDED`를 확인했다.

```sh
xcodebuild build -project Jday.xcodeproj -scheme Jday_macOS \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO \
  -derivedDataPath /private/tmp/zerosync-jday-check-eszwutg6/DerivedData
```

첫 빌드는 코딩 에이전트 샌드박스의 `sandbox-exec: sandbox_apply: Operation not permitted`로 Swift 매크로 실행이 실패했다. 같은 임시 복사본에서 샌드박스 제한 없이 다시 실행한 빌드는 성공했다. 최종 로그는 임시 폴더의 `macos-build-unrestricted.log`에 있다. 임시 경로는 정리될 수 있다.

최초 조사에서는 원본 Jday 파일, 봇 DB, Discord 채널·글, 실행 중인 봇 설정을 바꾸지 않았다. 테스트 타깃을 실행한 검증은 아니다.

### 승인 후 로컬 수정

- Jday의 `fix/0-regenerate-project` 브랜치에서 XcodeGen을 실행해 생성물을 갱신했다. 다중 부모 참조 0개, iOS·macOS 앱 각 58개와 위젯 17개 소스 경로가 모두 유효하고, 위젯 공유 소스 포함이 유지됨을 확인했다.
- 실제 Jday 작업 브랜치의 서명 없는 macOS 빌드도 성공했다. 검증 로그는 `/private/tmp/jday-fixed-build-uuuhyynb/build.log`다. iOS 빌드는 실행하지 않았다.
- 봇은 명령의 Xcode action과 출력으로 `build`·`test`·`unknown`을 저장한다. 빌드 결과는 “빌드 성공/실패”와 테스트 미실행 안내로, 테스트 0개나 실행 수 미확인은 그 사실을 표시한다. 종류를 모르는 과거 기록도 테스트 실행 수가 없으면 테스트 통과로 표시하지 않는다.
- Discord·PR·대시보드의 결과 본문, 아침 보고, 담당자 보고 근거에 같은 구분을 적용했다. 명령 성공 여부에 따른 파이프라인 전이는 유지한다.
- 변경은 로컬 작업 브랜치에만 있다. 봇 DB·Discord·실행 중인 프로세스는 변경하지 않았고 push하지 않았다.

## 재발 방지와 후속 작업

- Jday 재생성 결과를 검토한 뒤 봇이 사용하는 기준 브랜치에 반영한다. 기존 작업 worktree는 별도이므로 원본 폴더만 재생성해도 이미 멈춘 작업이 자동 복구되지는 않는다.
- 이전 보고 글이 없을 때 현재 제품 포럼에 대체 글을 만들고, 이후 반복 보고가 새 글을 사용하도록 기록하는 복구 처리를 검토한다. Discord 예외 변환은 입출력 계층에 둔다.
- 재알림을 작업별로 격리하고, 사라진 글을 대상으로 하는 작업의 재개·중지 경로를 검토한다.
- 실제 테스트 타깃 추가는 별도 제품 작업으로 결정한다.
- 운영 반영과 기존 `NEEDS_HUMAN` 작업의 정리는 아직 수행하지 않았다.
