# ADR-017 세 엔진(Claude·Codex·Gemini)의 권한 통일

2026-11-22 Zero 결정.

ADR-012의 "Codex 구현 허용" 절 가운데 "기획·디자인·설계 문서 단계는 Claude만 맡는다"와 운영 규약 1.3의 같은 문장을 대체한다.

## 배경

운영 규약 1.3은 "권한은 엔진이 아니라 단계별 담당에 붙는다"고 정했다. 그런데 실제로는 엔진마다 권한이 달랐다.

| 항목 | Claude | Gemini(Antigravity `agy`) | Codex |
|---|---|---|---|
| 맡을 수 있는 단계 | 전부 | 전부 | 읽기 단계와 구현·수정만 (R4) |
| 문서 단계 쓰기 범위 | 자기 폴더만 | 자기 폴더만 | 맡지 못함 |
| 개념 노트 웹 검색 | 허용 | 웹 가져오기 허용 (실제로는 검색만 된다, ADR-018) | 없음 |
| `.env` 변경 차단 | 도구 권한 | 도구 권한 | 없음 |

Codex만 다른 이유는 샌드박스가 폴더 단위라는 점이었다. `workspace-write`는 worktree 전체를 열어, 문서 단계를 `docs/기획/` 같은 폴더로 좁힐 수 없다. Zero는 엔진을 바꿔도 맡을 수 있는 일과 쓸 수 있는 범위가 같기를 원했다.

## 결정

1. **단계**: 세 엔진 모두 모든 단계를 맡는다. org.yaml 불러오기의 Codex 쓰기 단계 검사(R4의 엔진 조건), 파이프라인의 같은 검사, `cli.codex_models`의 단계 제한을 없앤다. R1(작성자와 리뷰어 분리)과 R6(팀장 확인)은 그대로다.
2. **쓰기 범위**: 단계별 쓰기 범위는 운영 규약 1.3 표 그대로다. 문서 단계 폴더는 `bot/agents/base.py`의 `DOC_STAGE_DIRS` 하나로 두고 Gemini 정책과 실행 뒤 검사가 함께 쓴다.
3. **Codex 실행**: 기획·디자인·설계·구현·수정은 `workspace-write`(worktree와 원래 저장소의 `.git`), 그 밖은 `read-only`. 웹 검색은 개념 노트만 `codex --search exec`로 켜고, 다른 단계는 `-c web_search="disabled"`로 끈다. codex-cli 0.161은 웹 검색이 기본으로 켜져 있기 때문이다. ChatGPT 앱·플러그인(`codex_apps` MCP)은 모든 단계에서 끈다(`--disable apps --disable plugins`). 웹 검색을 꺼도 앱의 검색 도구로 돌아가기 때문이며, Claude의 `--strict-mcp-config`와 같은 자리다.
4. **실행 뒤 검사 (엔진 공통)**: 쓰기 단계가 끝나면 봇이 실행 전 커밋과 HEAD의 차이(`git diff --name-only --no-renames`)를 본다. 문서 단계가 자기 폴더 밖을 바꿨거나, 어느 단계든 `.env`를 바꿨으면 형식 오류처럼 문제를 붙여 1회 다시 요청한다. 그래도 남으면 NEEDS_HUMAN으로 넘긴다(운영 규약 2.1). 커밋별이 아니라 실행 전후 차이를 보는 것은, 에이전트가 되돌린 변경까지 문제 삼지 않기 위해서다. Claude는 도구 권한으로 미리 막으므로 이 검사에 걸리지 않는 것이 정상이다. Gemini는 `.env`만 미리 막고, 문서 폴더 제한은 이 검사에 기댄다(결과 절).

## 결과

- 엔진을 바꿔도 맡는 일과 쓰기 범위가 같다. 회사 설정에서 엔진만 바꾸면 된다.
- 완전히 같지 않은 점이 남는다. Codex는 경로별 읽기 차단이 없어 `.env`와 볼트 `회사/`를 읽는 것은 막지 못한다. 막는 것은 실행 뒤 발견되는 변경뿐이다. 실제 저장소의 `.env`는 Codex의 쓰기 범위(worktree와 `.git`) 밖이고 worktree에는 체크아웃되지 않으므로, 쓰기 위험은 커밋 검사로 충분하다고 본다.
- Codex가 문서 단계에서 폴더 밖 파일을 고치면 Claude·Gemini와 달리 실행 중에는 막히지 않고 재요청 한 번을 쓴다.
- 2026-11-22 실제 호출로 확인했다(codex-cli 0.161, 러너 인자 그대로). 개념 노트는 웹 검색으로 답했고, 의견 단계는 "웹 검색 불가"로 답했다. 끄기 전에는 의견 단계도 웹 검색을 썼고, 웹 검색만 끄면 `codex_apps`의 `search_service.web_run`으로 돌아갔다.
- Gemini(Antigravity `agy` 1.5.14)의 웹 검색 도구 `search_web`은 권한 규칙(`read_url(*)`·`execute_url(*)` 차단, `search_web(*)`, `search_web`)으로도, `--mode plan`을 빼도 막히지 않고, 도구를 끄는 설정 키도 없다. 그래서 개념 노트 외 단계는 `tools`에서 `search_web`을 뺀 전용 에이전트(`byeolchae`)로 돌린다(같은 날 추가, 실제 호출로 확인). 러너가 실행 폴더의 `antigravity/.agents/agents/byeolchae.md`에 에이전트 파일을 쓰고 `--add-dir`·`--agent`로 고른다. `--agent`는 파일 경로를 받지 않는다. 구조화 출력은 `finish` 도구로 나오므로 `tools`에 넣어야 하고, 에이전트 본문이 기본 시스템 프롬프트를 대신하므로 일하는 방식(셸 명령을 묶지 않기, 거부 뒤 이어 가기, 끝에 답하기)을 본문에 적었다. 확인 결과: 같은 질문에 기본 에이전트는 `search_web`을 썼고 전용 에이전트는 "웹 검색 불가"로 답했다. 의견(구조화 출력), 구현(커밋과 구현 보고), 설계(문서 폴더 커밋)가 전용 에이전트로 돌았고, `.env` 거부도 그대로 들었다.
- 같은 확인에서 Gemini 러너가 실행되지 않던 것을 고쳤다. `agy`의 `-p`는 바로 뒤 인자를 프롬프트로 받고 stdin을 읽지 않는다. 지금은 `--input-format stream-json --output-format stream-json`으로 stdin에 프롬프트를 넘기고 마지막 `result` 이벤트를 읽는다. 의견(구조화 출력)과 개념 노트를 실제로 실행해 확인했다.
- Gemini 쓰기 권한도 같은 날 실제 호출로 확인했다(git worktree에서 설계·구현·`#비서` 대화 단계, 러너 설정 그대로).
  - 처음 규칙으로는 쓰기 단계의 git 명령이 하나도 돌지 않았다. 경로 규칙은 절대 경로만 받고 glob(`**`)을 쓸 수 없다. 그런데 `.env`(상대 경로)와 `**/.env`가 있어 터미널 샌드박스 설정 오류가 났다. 또 샌드박스는 `write_file` 허용 경로만 쓸 수 있어 `.git`에 쓰지 못했다.
  - 고친 뒤: `.env`·`회사/` 거부는 작업 폴더, `read_dirs`, 원래 저장소의 절대 경로로 쓴다. `read_file` 거부가 같은 경로의 쓰기도 막는다. 쓰기 단계는 `.git`(worktree면 원래 저장소의 `.git`) 쓰기를 연다. 그 결과 `.env`의 읽기·쓰기 거부, 원래 저장소 `.env` 읽기 거부, 커밋 성공, push 거부, 읽기 단계 파일 쓰기 거부, git 기록 읽기 성공을 확인했다.
  - 문서 단계 폴더 제한은 실행 중에는 걸 수 없다. 어느 규칙에도 맞지 않는 쓰기는 기본 정책에서 허용되고, `toolPermission: strict`는 `allow`를 무시하고 모든 쓰기를 막는다. `Deny > Ask > Allow` 순서라 "전부 막고 한 폴더만 허용"도 만들 수 없다. 그래서 Gemini 문서 단계는 Codex처럼 실행 뒤 검사(결정 4)가 폴더 밖 변경을 잡는다. 실행 중에 미리 막는 것은 Claude뿐이다.
  - 어느 규칙에도 맞지 않는 셸 명령(`ls`, `git rev-parse` 등)은 헤드리스 실행에서 거부되면서 그 자리에서 턴이 끝나고 빈 응답이 나왔다. 명시적 거부 규칙에 걸린 명령(push)은 거부 뒤 남은 일을 이어 갔다. 그래서 git을 허용하는 단계는 git이 아닌 명령을 정규식 거부 규칙(`command(regex:[^g].*)` 등 4개)으로 막는다. 규칙 안에 괄호를 쓰면 규칙이 읽히지 않았고, agy 정규식에는 lookahead가 없어 첫 글자로 나눴다. 허용 목록 밖의 git 하위 명령(`checkout` 등)은 아직 턴을 끝낼 수 있다.
